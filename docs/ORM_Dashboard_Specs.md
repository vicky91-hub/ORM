# ORM Performance Dashboard — Build Specs & Conventions
*Sumadhura — Social / GMB / Reddit / Quora. Reference this file whenever rebuilding, refreshing, or extending the dashboard.*

## Deliverable
Single-file interactive HTML dashboard (`ORM_Performance_Dashboard.html`), styled to the North Star Digital brand guide (see `NSD_Brand_Guidelines.md`). Built with vanilla JS + Chart.js (CDN). Uses `window.storage` (Claude artifact persistent storage, `shared:true`) for cross-session/cross-user history.

Confirmed identities:
   - **Capitol Residences** and **Capitol Towers** are two distinct real projects — never merge them.
   - **"Hive and Thrive"** = *Sumadhura Hive* on Google.
   - **"Infracon"** = *Sumadhura Infracon Private Limited*.
   - **GBTB was dropped** — no June/July activity, and the user didn't recognize it as a real handle. (It does appear in the sheet's Feb–May data and the `Q1` rollup tab, so don't reintroduce it without asking again.)
   - The 11 confirmed projects: Folium, Edition, Capitol Residences, Panorama, Capitol Towers, Elysium, Infracon, Z-hub, Hive and Thrive, Solace, Epitome.

## Section-by-section rules

### Weekly Delivery Overview
Activity only (posts/comments/responses), by platform, W1–W3. Not a sentiment measure — say so in the UI.

### Sentiment Analysis
Donut breakdowns per platform (Reddit, GMB, Social) + one combined "Sentiment by Platform" stacked bar for Social (Instagram/Facebook/GMB/LinkedIn) with a plain totals table.
- **Do not show a "responded" column in the social platform breakdown.** That table is for activity volume + sentiment only — response coverage lives elsewhere (GMB negative-review cards, Reddit/Quora delivery-vs-target).
- **Social Sentiment Trend is week-on-week, not day-by-day.** Roll the daily tracker rows up into Monday–Sunday buckets before charting (see `mondayOf()` / `socialWeekly` in the code) — day-to-day is too noisy to be useful. Label any trailing incomplete week "(partial)".

### Reddit — New Post Outcomes
Only show posts with real outcome data (upvotes/comments/sentiment populated). **Do not include a "Scheduled" / not-yet-published section** — if a post hasn't gone live yet, leave it out entirely rather than showing a placeholder card.

### GMB — Project Performance
- Scoped to the **11 confirmed projects from the June+July tabs** (see Data sources above) — not the broader Jan-Jul history, not the full Handle-tab list.
- Columns are **"Current Rating"** (live Google pull) and **"Last Month Rating"** (not "Tracker Avg" — renamed per user request). Behavior:
  - **This first time only**, "Last Month Rating" is hardcoded from the June-2026 tab's per-project average (a true single-month figure) — three projects (Solace, Epitome, Hive and Thrive) had zero June reviews, so they show "No Jun data" rather than a fabricated number.
  - **Going forward, this column is self-updating**: at render time, look up `gmb_rating_history:{project}:{prevMonthKey}` in shared storage first; if a month-end auto-save exists for the prior month, use that value (marked with a ● indicator) instead of the hardcoded baseline. `prevMonthKey()` computes the month before `REPORT_MONTH` — bump `REPORT_MONTH` each refresh and this cascades automatically.
  - `REPORT_MONTH` and its helpers (`prevMonthKey`, `monthLabel`) live near the top of the script (not buried in the Rating History section) since the GMB table needs them too.
- **Top 3 / Bottom 3 panel**, ranked by live rating. Tie-break: for the *top* (best) list, higher review count wins the tie (more confidence). For the *bottom* (worst) list, higher review count should also rank *first* among ties — a low rating backed by hundreds of reviews is a bigger signal than the same rating on a handful of reviews. (Sort direction differs between the two lists — don't reuse one sorted array and reverse-slice it, compute each independently.)
- **Rating History (month-on-month):**
  - Seed with **two** real data points: June (from `gmbProjects.lastMonthRating`, now a genuine June-only average) and July (current month's live pull). See "Data & Methodology" section below for why this changed back and forth — short version: once `lastMonthRating` stopped being a multi-month blend, showing June as a real point became legitimate again.
  - **Auto-save runs on the last calendar date of every month**, no user action required. On page load, check if today is month-end (`isLastDayOfMonth()`); if so, silently snapshot every project's current live rating to `gmb_rating_history:{project}:{YYYY-MM}` (shared storage), skipping projects that already have that month saved. This is the same storage the "Last Month Rating" column reads from — one write path, two read paths.
  - Manual "Save this month's snapshot" button remains only as an off-cycle backup, not the primary mechanism.
  - **Known limitation to keep surfacing in the UI:** this is a static file. Auto-save triggers correctly off the real calendar, but it snapshots whatever `liveRatings` values are baked into that file version — if the file itself isn't refreshed with a fresh Google Places pull before month-end, the "auto-saved" snapshot will just be stale data relabeled. True hands-off accuracy needs either (a) someone regenerating the file with a fresh pull shortly before month-end, or (b) a live data connector instead of a static snapshot. Say this plainly rather than implying full automation.

### Negative Review Themes
- **Scope: latest complete Monday–Sunday week only**, computed automatically from an `ANCHOR_DATE` constant (bump this each refresh) via `getLastCompleteWeek()` — never hand-pick a date range.
- Group raw dated review records (rating ≤3★) by project within that window; show count, priority, response status, and a paraphrased narrative per review (not verbatim — this is customer data, paraphrase for a clean read, but factual specifics are fine since it's the business's own review inbox, not third-party copyrighted content).
- Flag data-quality oddities plainly when spotted (e.g. identical complaint text logged against two different projects on the same date — likely a mis-tagged entry).
- Same month-end caveat as above: the "auto-update every Monday" *logic* is real (the week-window math is dynamic), but the underlying raw review records still need a fresh pull each week for the content itself to be current.

## Data & Methodology (kept HERE only — user asked to remove this from the dashboard UI entirely; surface it only if they ask, not on the page)
- **GMB — Project Performance table**: project list locked to the 11 projects appearing in the June and July 2026 GMB Tracker tabs. "Current Rating" = live Google Places pull. "Last Month Rating" = average of each project's June-2026 star ratings specifically (4–5★ positive, 3★ neutral, 1–2★ negative). "Reviews (Jun–Jul)" and the sentiment split are combined June+July counts.
- **Rating History**: first data point = June (from `gmbProjects.lastMonthRating`, a genuine June-only average — legitimate to show as a real point, unlike the old multi-month blend this field used to be). Second point = July, from the live pull (`REPORT_MONTH`). On page load, checks whether today is the last calendar date of the month; if so, auto-saves every project's live rating to shared storage under key `gmb_rating_history:{project}:{YYYY-MM}`. The GMB table's "Last Month Rating" column also checks this same storage for a saved snapshot of the prior month before falling back to the hardcoded June baseline.
- **Negative Review Themes**: scoped to the latest *complete* Monday–Sunday week only, computed from an `ANCHOR_DATE` constant — not the visitor's device clock. Bump `ANCHOR_DATE` and refresh the raw review records each time this report is regenerated.
- **Weekly Delivery Overview / KPI strip**: sourced directly from the Summary tab's activity-tracking rows — volume only, not sentiment.
- **Sentiment Analysis (Reddit / GMB / Social / Quora pies)**: Reddit from the Reddit & Quora Content Plan's Summary tab. GMB from June+July categorized reviews. Social summed from "Sumadhura daily report," 22 Jun–13 Jul 2026. **Quora sentiment is real, not scraped** — sourced from the Reddit & Quora Content Plan sheet's own per-thread `Positive comments` / `Negative Comments` columns on the "Quora - New + Existing" tab (5 published threads, 27 total comments, 24 positive / 0 negative / 3 unclassified-as-neutral). Don't try to live-scrape Quora for this — the sheet already tracks it, just wasn't being surfaced before.
- **KPI strip has two scopes** (toggle buttons: "This Week (W3)" / "Full Period (22 Jun–13 Jul)") so all 4 KPI cards share the same time window and don't create the "207 vs 1,270" confusion of mixing a weekly number with a full-period number in the same strip. Week values: Total Activity 207, New Posts 8, GMB Neg Responded 6, Social Comments 430 (week-3-only social, computed by filtering `socialWeekly` to the W3 bucket). Full-period values: 654, 13, 9, 1,270. Keep these as explicit hardcoded objects (`kpiScopes.week` / `kpiScopes.full`) rather than derived live, so the source sum is traceable.

## Resilience notes
- Wrap all `Chart.js` instantiation in a `typeof Chart !== 'undefined'` guard (and try/catch) — a slow/blocked CDN load must not prevent tables, cards, and other plain-DOM rendering from working.
- Guard every `window.storage` call — it won't exist outside the Claude artifact runtime (e.g. local preview) and should degrade to a clear inline message, not a thrown error.
- **Tab-filter rule (fixed twice — get this exactly right):** sections tagged `data-platform="all"` are only exempt from hiding if they contain their own inner `[data-platform]`-tagged descendants (e.g. Sentiment Analysis, which holds per-platform donuts/cards that do their own filtering). An "all" section with **no** inner platform-tagged children (KPI strip, Weekly Delivery Overview) must hide like any other section when a specific tab is selected — otherwise those sections stay visible on every tab and the dashboard looks like tab-switching does nothing at all, which is exactly what got reported twice. The rule in code: `const hasInnerFilters = !!sec.querySelector('[data-platform]'); sec.classList.toggle('hidden', !hasInnerFilters && target !== 'all')`. Test this by checking, for every tab, which section `<h2>`s are actually visible (`!!el.closest('section').offsetParent`) — don't just check that the *target* platform's section shows; also confirm every *non-matching* section, including the "all"-tagged ones without inner filters, is actually hidden.
